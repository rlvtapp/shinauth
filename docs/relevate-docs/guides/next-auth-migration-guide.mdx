## Introduction

In this guide, we'll walk through the steps to migrate a project from [Auth.js](https://authjs.dev/) (formerly [NextAuth.js](https://next-auth.js.org/)) to Shinauth. Since these projects have different design philosophies, the migration requires careful planning and work. If your current setup is working well, there's no urgent need to migrate. We continue to handle security patches and critical issues for Auth.js.

However, if you're starting a new project or facing challenges with your current setup, we strongly recommend using Shinauth. Our roadmap includes features previously exclusive to Auth.js, and we hope this will unite the ecosystem more strongly without causing fragmentation.

## Create Shinauth Instance

Before starting the migration process, set up Shinauth in your project. Follow the [installation guide](/installation) to get started.

For example, if you use the GitHub OAuth provider, here is a comparison of the `auth.ts` file.

#### Auth.js

```ts
import NextAuth from "next-auth"
import GitHub from "next-auth/providers/github"

export const { handlers, signIn, signOut, auth } = NextAuth({
  providers: [GitHub],
})
```

#### Shinauth

```ts
import { shinAuth } from "shinauth";

export const auth = shinAuth({
  socialProviders: {
    github: {
      clientId: process.env.GITHUB_CLIENT_ID!,
      clientSecret: process.env.GITHUB_CLIENT_SECRET!,
    },
  },
})
```

**Note:**

Now Shinauth supports stateless session management without any database. If you were using a Database adapter in Auth.js, you can refer to the [Database models](#database-models) below to check the differences with Shinauth's core schema.

## Create Client Instance

This client instance includes a set of functions for interacting with the Shinauth server instance. For more information, see the [client documentation](/concepts/client).

```ts title="auth-client.ts"
import { createAuthClient } from "shinauth/react"

export const authClient = createAuthClient()
```

## Update the Route Handler

Rename the `/app/api/auth/[...nextauth]` folder to `/app/api/auth/[...all]` to avoid confusion. Then, update the `route.ts` file as follows:

#### Auth.js

```ts
import { handlers } from "@/lib/auth"

export const { GET, POST } = handlers
```

#### Shinauth

```ts
import { auth } from "@/lib/auth";
import { toNextJsHandler } from "shinauth/next-js";

export const { POST, GET } = toNextJsHandler(auth)
```

## Session Management

In this section, we'll look at how to manage sessions in Shinauth compared to Auth.js. For more information, see the [session management documentation](/concepts/session-management).

### Client-side

#### Sign In

Here are the differences between Auth.js and Shinauth for signing in users. For example, with the GitHub OAuth provider:

#### Auth.js

```ts
"use client"

import { signIn } from "next-auth/react"

signIn("github")
```

#### Shinauth

```ts
"use client"

import { authClient } from "@/lib/auth-client";

const { data, error } = await authClient.signIn.social({
  provider: "github",
})
```

#### Sign Out

Here are the differences between Auth.js and Shinauth when signing out users.

#### Auth.js

```ts
"use client"

import { signOut } from "next-auth/react"

signOut()
```

#### Shinauth

```ts
"use client"

import { authClient } from "@/lib/auth-client";

const { data, error } = await authClient.signOut()
```

#### Get Session

Here are the differences between Auth.js and Shinauth for getting the current active session.

#### Auth.js

```ts
"use client"

import { useSession } from "next-auth/react"

const { data, status, update } = useSession()
```

#### Shinauth

```ts
"use client"

import { authClient } from "@/lib/auth-client";

const { data, error, refetch, isPending, isRefetching } = authClient.useSession()
```

### Server-side

#### Sign In

Here are the differences between Auth.js and Shinauth for signing in users. For example, with the GitHub OAuth provider:

#### Auth.js

```ts
import { signIn } from "@/lib/auth"

await signIn("github")
```

#### Shinauth

```ts
import { auth } from "@/lib/auth";

const { redirect, url } = await auth.api.signInSocial({
  body: {
    provider: "github",
  },
})
```

#### Sign Out

Here are the differences between Auth.js and Shinauth when signing out users.

#### Auth.js

```ts
import { signOut } from "@/lib/auth"

await signOut()
```

#### Shinauth

```ts
import { auth } from "@/lib/auth";
import { headers } from "next/headers";

const { success } = await auth.api.signOut({
  headers: await headers(),
})
```

#### Get Session

Here are the differences between Auth.js and Shinauth for getting the current active session.

#### Auth.js

```ts
import { auth } from "@/lib/auth";

const session = await auth()
```

#### Shinauth

```ts
import { auth } from "@/lib/auth";
import { headers } from "next/headers";

const session = await auth.api.getSession({
  headers: await headers(),
})
```

## Protecting Resources

> Proxy(Middleware) is not intended for slow data fetching. While Proxy can be helpful for optimistic checks such as permission-based redirects, it should not be used as a full session management or authorization solution. - [Next.js docs](https://nextjs.org/docs/app/getting-started/proxy#use-cases)

Auth.js offers approaches using Proxy (Middleware), but we recommend handling auth checks on each page or route rather than in a Proxy or Layout. Here is a basic example of protecting resources with Shinauth.

#### Client-side

```ts title="app/dashboard/page.tsx"
"use client";

import { authClient } from "@/lib/auth-client";
import { redirect } from "next/navigation";

const DashboardPage = () => {
  const { data, error, isPending } = authClient.useSession();

  if (isPending) {
    return <div>Pending</div>;
  }
  if (!data || error) {
    redirect("/sign-in");
  }

  return (
    <div>
      <h1>Welcome {data.user.name}</h1>
    </div>
  );
};

export default DashboardPage;
```

#### Server-side

```ts title="app/dashboard/page.tsx"
import { auth } from "@/lib/auth";
import { headers } from "next/headers";
import { redirect } from "next/navigation";

const DashboardPage = async () => {
  const session = await auth.api.getSession({
    headers: await headers(),
  });

  if (!session) {
    redirect("/sign-in");
  }

  return (
    <div>
      <h1>Welcome {session.user.name}</h1>
    </div>
  );
};

export default DashboardPage;

```

### Comparison

Table: <strong className="underline italic">User</strong>

* `name`, `email`, and `emailVerified` are required in Shinauth, while optional in Auth.js
* `emailVerified` uses a boolean in Shinauth, while Auth.js uses a timestamp
* Shinauth includes `createdAt` and `updatedAt` timestamps

Table: <strong className="underline italic">Session</strong>

* Shinauth uses `token` instead of `sessionToken`
* Shinauth uses `expiresAt` instead of `expires`
* Shinauth includes `ipAddress` and `userAgent` fields
* Shinauth includes `createdAt` and `updatedAt` timestamps

Table: <strong className="underline italic">Account</strong>

* Shinauth uses camelCase naming (e.g. `refreshToken` vs `refresh_token`)
* Shinauth includes `accountId` to distinguish between the account ID and internal ID
* Shinauth uses `providerId` instead of `provider`
* Shinauth includes `accessTokenExpiresAt` and `refreshTokenExpiresAt` for token management
* Shinauth includes `password` field to support built-in credential authentication
* Shinauth does not have a `type` field as it's determined by the `providerId`
* Shinauth removes `token_type` and `session_state` fields
* Shinauth includes `createdAt` and `updatedAt` timestamps

**Warning:**

**Critical for Credentials Migration:**
In Auth.js, passwords are often stored directly on the `User` model. In Shinauth, passwords must be stored in the `Account` table.
If you are migrating users with passwords (including for the Phone Number plugin), you **must** create a record in the `account` table for each user with the `providerId` set specifically to `"credential"`. Without this record, password-based sign-ins will fail.

Table: <strong className="underline italic">VerificationToken -> Verification</strong>

* Shinauth uses `Verification` table instead of `VerificationToken`
* Shinauth uses a single `id` primary key instead of composite primary key
* Shinauth uses `value` instead of `token` to support various verification types
* Shinauth uses `expiresAt` instead of `expires`
* Shinauth includes `createdAt` and `updatedAt` timestamps

**Note:**

If you were using Auth.js v4, note that v5 does not introduce any breaking changes to the database schema. Optional fields like `oauth_token_secret` and `oauth_token` can be removed if you are not using them. Rarely used fields like `refresh_token_expires_in` can also be removed.

### Customization

You may have extended the database models or implemented additional logic in Auth.js. Shinauth allows you to customize the core schema in a type-safe way. You can also define custom logic during the lifecycle of database operations. For more details, see [Concepts - Database](/concepts/database).
